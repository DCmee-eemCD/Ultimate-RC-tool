## Architecture decided

- Key entry belongs on an extension-origin options page (`llm-settings.html`), not MAIN-world tool DOM. This keeps secrets separate from the website and theme export.
- Background helper global `RCLLM.handle(message, sender)` loaded with `importScripts('llm.js')` in `extension/background.js`.
- `llm-config-get` / `llm-config-save`: only extension options page sender. Return `{endpoint, model, hasKey}`, NEVER the raw key. Blank key on save retains key; explicit `clearKey` deletes it.
- Store config under `chrome.storage.local.rcLlmConfig`; not sync. Endpoint defaults to `https://api.openai.com/v1`; model ID entered by user.
- `llm-answer`: only trusted extension content script, top frame, EduNext origin. Question limit 24,000 chars; answer limit 4,000 chars. HTTPS endpoint (HTTP loopback allowed), reject URL credentials/query/hash, no redirects that leak authorization, no automatic retries, timeout ~45 seconds. Short Vietnamese answer instruction; never log keys or echo raw provider errors.
- Parent still needs to add `llm-settings-open` handler using `chrome.runtime.openOptionsPage()` and manifest `options_page`.
- New isolated-world content script should expose Answer + API settings beside composer. No API key in DOM/MAIN-world bridge. Prefer one-click flow initially.
- Backend results follow existing `{result}` / `{error}` runtime response envelope.

## Critical security issue to fix BEFORE storing a key

`extension/bridge.js` currently reads `chrome.storage.local.get(null)` and sends ALL values to MAIN world in `rcExtension:init`; it also forwards ALL local storage changes. Filter both initial snapshots and onChanged events to the existing `allowedKey` allowlist (`chatKit`, `chatKitBgVid`, `rc_ocr_*`). Otherwise future `rcLlmConfig` secrets leak to the website. Do not add LLM operations to the window.postMessage bridge. Existing allowedKey restricts writes only, not reads.
